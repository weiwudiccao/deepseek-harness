# Agent Note: 隔离员工运行时并显示已认证身份

Status: implemented

[English](2026-09-01-employee-runtime-isolation-and-identity.md) | 中文

## 问题

使用员工认证的部署可以验证多个 OA 账号，但仍可能把所有账号代理到同一个 DSH 进程。由于一个进程只解析一份 `DSH_HOME`，此时每名已认证员工都会看到相同的持久会话、设置和浏览器认证 Cookie。客户端筛选行不能落实隔离，因为底层 API 和 WebSocket 仍然公开共享运行时。

同一部署也缺少当前员工的可见确认。用户可以成功认证，却看不到权威 OA 记录返回的员工姓名和岗位名称。

## 决策

认证网关按已认证 OA User id 确定运行时归属。它派生不可逆且可安全用于文件名的键，在网关用户数据根目录下创建一份持久 home，并按需启动一个 loopback DSH 进程，把 `HOME` 和 `DSH_HOME` 都设置到该员工目录中。同一员工的并发请求共享一个启动 Promise 和一枚 DSH 浏览器 Cookie；不同员工使用不同目录、进程、端口和 Cookie。HTTP 与 WebSocket 请求先解析已认证网关会话，再选择运行时。

OA 登录响应是身份权威来源。网关只保留稳定的 User id、员工 id、员工姓名、岗位名称、OA 会话 Cookie 和网关会话时序；绝不保留用户提交的密码。`/auth/session` 向已认证浏览器会话返回员工展示字段。

设置外壳在侧边栏底部提供可选的 `settings.account` 席位。`@deepseek-ai/dsh-client-ui-employee-identity` 使用同源凭据且禁用 HTTP 缓存来读取 `/auth/session`，校验网络响应后以员工姓名、岗位名称和姓名首字头像替换直接「设置」触发器。「设置」显示在账号菜单中，并通过外壳提供的回调打开，因此设置包继续持有面板生命周期。折叠轨道保留姓名首字头像，并通过提示框提供两个资料值。该包不会在浏览器存储中持久化身份；资料不可用时恢复直接「设置」触发器。

这条边界隔离由 DSH 拥有的会话、设置、凭据和其他以 `DSH_HOME` 为根的数据。它不会为每名员工创建独立源码检出或文件系统工作区：部署仍独立决定工作目录和文件系统策略。

## 验证

网关测试固定稳定且不同的存储键、同员工启动合并、不同 `DSH_HOME`、运行时清理、逐用户 HTTP 路由、不同 DSH Cookie，以及 `/auth/session` 返回的员工字段。客户端测试固定响应校验、展开状态下的姓名／岗位渲染、折叠状态渲染、点击后显示「设置」的行为、资料不可用回退、slot 生命周期和侧边栏快照。

## 考虑过的替代方案

**在浏览器中筛选共享会话。** REST 与 WebSocket 表面仍然共享，客户端缺陷或直接请求仍可越过表面边界。

**使用单一 DSH 进程并为会话 id 添加员工前缀。** DSH 拥有的不只有会话 id，还包括设置和凭据等持久状态。只为一种记录添加前缀会让其余状态保持共享，并迫使不相关的包都理解员工身份。

**为每名员工创建固定 systemd 单元和端口。** 员工清单会动态变化，固定端口需要单独分配，非活跃员工也会占用进程。网关按需拥有进程，可以在无需预配置所有账号的同时保留持久 home。

**在 `ui-sidebar` 中获取员工信息。** 侧边栏是组合外壳。可选的设置账号席位让部署认证保持在通用外壳之外，也让没有员工网关的部署保留外壳直接显示的「设置」触发器。

## 影响

两名已认证员工无法通过网关访问对方由 DSH 拥有的会话历史，因为各自请求终止在不同进程和持久 home。网关重启会停止其子进程，而逐员工 home 会继续保留，并在下次请求时按需重启。

部署的代价是每名活跃员工占用一个 Node 进程，直到网关重启。如果实际并发规模需要，可以在运行时 provider 边界增加容量限制和空闲回收。配置的共享工作目录下的文件仍受部署现有文件系统权限约束，不属于会话隔离范围。
